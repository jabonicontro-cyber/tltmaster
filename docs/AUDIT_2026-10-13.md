## 5. Security, data integrity, tenant isolation

- New server actions check permissions on the server (`approvePlanAssignments`: `dispatch.edit`; `dismissDemoWelcome`:
  demo company only, and the database function refuses real companies). New pages use `requirePagePermission`.
- New reads go through the user's own session (RLS); no service-role key in app code paths added today.
- Approvals re-validate with fresh data and assign through the database function that re-checks eligibility,
  capacity, conflicts and permissions; a re-submitted approval cannot double-assign (the load is no longer open).
- Demo samples refuse non-demo companies (`ensureFeatureSamples` → `demoCompany`); tests cover the refusal.
- Known privacy trade-off (documented in DEMO_TENANTS §2): in the presenter demo the header shows the presenter's own
  profile photo if they have one (name stays the persona).
- No hosted migrations pending: hosted `migration list` shows every migration Local and Remote (owner, 2026-10-13).

## 6. Duplicates and conflicts

- Two recommendation surfaces share one constraint source: Smart Dispatch (per load, on the Dispatch board) and Plan
  the day (whole day). Both use `checkPair`; scoring differs by design. A dispatcher could approve conflicting proposals
  from both only sequentially — the second is refused by `assign_load`.
- Two readiness views will need one evaluator: `/setup` (data readiness) now; the AI readiness dashboard (B15) must
  reuse `src/lib/onboarding/readiness.ts` rather than recompute.
