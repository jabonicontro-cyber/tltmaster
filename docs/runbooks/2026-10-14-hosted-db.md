### Rollback rules (corrected)

- Newest first. Run each script with `psql -v ON_ERROR_STOP=1 -1 -f <file>` so a failed guard stops the whole script
  (the two `20261115…` scripts have their own BEGIN/COMMIT: use `-v ON_ERROR_STOP=1` only).
- **Never run the `20261120000600` rollback while `20261120000900` is applied**: it drops `private.platform_settings`,
  which holds the MFA emergency key and which `require_platform_admin()` reads, and it switches permanent delete back on.
- **Destructive — backup and your explicit decision first:** `20261115000200` (directions verification data),
  `20261119000100` (prospect, tag and account-owner data despite its guard), `20261120000200` (per-person base limits:
  restricted people regain every base — a security change), `20261120000400` (help feedback and support requests),
  `20261120000700` (all portal data), `20261120000900` (recovery codes, security events, company MFA policies),
  `20261120001000` (all onboarding checklists and their history; stored files stay in the bucket),
  `20261120001200` (setup state and username reservations: people still on a temporary password could then use the
  app without choosing their own; turn those sign-ins off first), `20261120001500` (every Onboarding Kit form, its
  versions and the go-live sign-offs; activation stops waiting for the acceptance).
- Not destructive: `20261120002100`, `20261120002000` and `20261120001800` (no data, but **security** regressions: they
  re-open base access to the records they cover; roll back newest first), `20261120001900` (restores the earlier view
  definition), `20261120001600` (drops the index only), `20261120001700` (no data, but a **security** regression:
  base-limited people see every base's Command Center items again), `20261120001400`, `20261120001300` (new-format references stay; sequences return to the old
  format), `20261120001100` (restores earlier function definitions), `20261119000200` (read-only function;
  rollback file added 2026-10-19).
- A full restore (`pg_restore`, §12) overwrites everything written after the backup — ask me first.
- The Supabase CLI is not pinned in the repository (`npx supabase` resolves the latest); the per-migration transaction
  behaviour described in §12 is the CLI's, not something this repository controls.
